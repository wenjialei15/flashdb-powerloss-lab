位置是"第 N 次擦写之前掉电"。这些是实验台跑出来的现象，尚未向上游确认。

同一个负载，在这两个点断电后，fdb_tsl_iter 返回负的时间戳、负载与时间戳对不上的记录，超过 5000 条仍未结束。

第一条记录的 time 已经是 1801739606，而本次写入范围是 100000–100519。

怎么做的

没有复刻 FlashDB，跑的是上游源码。

FlashDB 本来就有 FAL 抽象层：把 Flash 设备换成 64 KB 内存模型，所有擦写就都经过同一个函数。

在那里计数，数到第 N 次就 longjmp 出去——这次操作不执行，等价于"在它之前掉电"。

关键是 NOR 语义：写入必须是 flash &= data，只能把 1 变 0。

如果用 memcpy，"没擦除就写"这种错误状态会被悄悄修好，测出来的全是假绿灯。

static int sim_write(long off, const uint8_t *buf, size_t size)
{
    if (size == 0) return 0;

    g_ops++;
    if (g_cut_at > 0 && g_ops >= g_cut_at) {
        longjmp(*g_cut_env, 1);      /* 断电：这次写不执行 */
    }

    for (size_t i = 0; i < size; i++)
        g_flash[off + i] &= buf[i];   /* NOR：只能清 0 */
    return 0;
}

这个结果意味着什么

2454 个点里 2449 个正常恢复，说明 FlashDB 的状态机整体是成立的。

剩下 5 个点集中在两处：KV 的 GC 恢复、TSDB 的扇区轮转。它们都遵循"先写元数据、再搬数据"，顺序被打断后，恢复逻辑可能删错项、误判库满，或者按坏掉的扇区头继续遍历。

它们不是已确认的上游 bug：没有提 issue，也没有补丁。实验台只负责把现象稳定复现出来。

复现命令：./build/powerloss-lab cut 46、cut 1546、cut 1550。可以直接提交的 issue 草稿放在仓库的 docs/issue-draft.md。

边界

  • 只模拟"操作之前"掉电，不模拟擦除做到一半、写入只完成一部分的物理时序。
  • 单线程，不覆盖多任务并发写同一个库。
  • 重启是进程内清零 + 重新 init，不等价于真实复位的外设状态。
  • 这套东西是验证工具，不能替代真机的高低温与老化测试。
